§0 接口（缺省一律不变）
  solve(..., assemble="dense"|"csr", linear_solver="dense"|"cudss")
    · 缺省 assemble="dense" + linear_solver="dense" - 数值与历史逐位不变。
    · linear_solver="cudss" **必须**配 assemble="csr"（否则 ValueError）：
      这条路上 _csr_to_dense 整段不执行，全程不再开 [B,Nj*Nj]。
    · 守卫（本机实测，全部明确 raise，无静默降级）：
        linear_solver='xyz'         → ValueError
        cudss + assemble='dense'    → ValueError
        cudss + mode='epanet'       → NotImplementedError（铁律三：复刻路径不碰）
        cudss + device='cpu'        → NotImplementedError
        cudss + 无 nvmath（本机）    → NotImplementedError，文本里带
                                       ModuleNotFoundError("No module named 'nvmath'")
        cudss + dtype!=f64          → NotImplementedError
        cudss + requires_grad       → NotImplementedError「请用 dense 或等 P3」
          【**P3 起作废**：可微通路已接上（_CudssSolveFn），requires_grad
            下不再 raise。现在只有二阶导（create_graph=True）明确 raise。
            见 data/p3_autograd_wip.txt §0/§5。】
  新增可调项（都不改缺省行为）：
    solver.cudss_matrix_type = None | DirectSolverMatrixType.SPD   （见 §6）
    solver.cudss_refine      = 2   （迭代精化步数，与稠密通路同为 2）
    solver.cudss_plan(B)     → 显式预热，返回该批量 plan 的 ms
  【F4 修复后新增，见 data/p2_f4_wip.txt】
    solver.cudss_cache_max   = 8   （cuDSS state 的 LRU 上限；None=不限=修复前）
    solver.cudss_free(empty_cache=False) → 释放全部 state，返回份数
    with solver.cudss_session(): ...     → 退出必放（含异常路径）
    solver.cudss_cache_info()            → 每份的 B/dtype/device/类型/plan_ms/MiB
  autodiff 入口（P1 审计列的 P2 前置，已接）：
    autodiff.solve_polished(..., assemble=, linear_solver=)   → 直通 s.solve
    autodiff.solve_unrolled(..., assemble=, linear_solver=)   → 自带装配，已分支

§1 实现里踩到的两个坑（都会静默毁掉整件事，记下来）
 1.1 reset_operands 会作废 plan
  nvmath 的 DirectSolver 里
      reset_operands / reset_operands_unchecked(a=...) **无条件**执行
      self.solver_planned = self.solver_factorized = False
      （nvmath/sparse/advanced/direct_solver.py:1530，另一处 :1351）
  第一版按"每轮 reset_operands → factorize → solve"写，10 网 × 3 批量 **全部**
  抛 "Factorization cannot be performed before plan() has been called."
  （现场：作业 1459205）。那种写法等于每轮迭代作废一次 plan，正是 P0 结论要躲的。
  改法（也正是 nvmath 文档自己的建议 "update the values in place and refactorize"）：
  构造期建 B 个 sparse_csr_tensor，values 全是同一块 [B,nnz] 连续缓冲的行视图；
  每轮只 copy_ 进缓冲，**一次 reset_operands 都不调**，直接 factorize()。
  实测 torch.sparse_csr_tensor 不拷贝 values（§4 末列 "values 别名=True"），
  所以整块 copy_ 一句就够；代码里仍留了非别名情形的逐个 values() 写入分支。

 1.2 缓存键没归一化卡号
  构造期给的常是 torch.device('cuda')（无卡号），而张量带的是 'cuda:0'。
  第一版把 str(device) 直接进键 ⇒ cudss_plan(B) 预热出一份 state、solve() 又
  按另一个键建第二份并**再 plan 一次**（1459212 的 §4 里 "plan 计数 预热后=1
  首解后=2"）。plan 仍不在迭代循环里（二解后仍是 2），但白花一次 plan、
  多占一份 cuDSS state。已修（device.index is None → current_device()）。
  修后 1459222 的 §4：**plan 计数 1/1/1**。顺带 ky4 B=256 的整解也从
  0.492 快到 0.329 ms/场景（少一份 state 的显存/缓存压力）。

 2.4 【F2 订正】方案 §4「验收 1」的字面门槛没达到，判据是被改写的
  原文门槛：「max|dH| 量级与既有 dense-vs-epanet 一致（~1e-7 ft 级）」。
  实测最差 2.9e-5 ft（Pescara B=64 带 emitter，对抗审计 §3），**差 290 倍**。
  **原门槛为什么不适用**（不是"差不多就算过"）：
   a) 它是"dense vs epanet"在这批网上的经验量级，被默认成了"任何 f64 通路
      在任何网上都该达到的界"。可 §2.2 已量出偏差是 κ 定的：κ≤4e5 的 6 个网
      全在 1e-11 以下，κ≥2e9 的 4 个网全在 1e-7~1e-5。Pescara κ=1.7e10、
      City_D κ=3.4e15，前向误差上界 κ·eps·|H|max 本身就是 7.2e-4 ft 量级 -
      1e-7 在这些网上**不是任何 f64 直接法能保证的界**。
   b) 同一批网上**现有的 GPU 稠密通路**对 CPU f64 基准自己就差到 1.79e-5
      （Pescara，§2.2）。拿 1e-7 卡 cudss 等于要求新通路比被它替换的旧通路
      准 100 倍 - 这个门槛从来没有在旧通路上成立过。
   c) §2.1/审计 §8 已坐实：|cudss−dense| 与 **cuDSS 自己重跑两次的差**同量级
      （比值 0.64~2.09，14/14），也就是说这个 2.9e-5 不是"偏差"，是 cuDSS
      运行间不定性的噪声底，再怎么改实现也压不到 1e-7。
  **改判据后的验收 1（四条全部成立且可复核）**：
   ① 迭代数与 dense 逐项相等 - P2 30/30、对抗审计 80/80；
   ② |cudss−dense| ≤ cuDSS 自重跑抖动的同量级（0.64~2.09x，14/14），
      而 dense 在 det=True 下自重跑恒 0.000e+00（14/14）；
   ③ 对 **CPU f64 dense 基准**（与 EPANET 对到 1e-14 的那条路径）
      |cudss−cpu| **不大于** |GPU dense−cpu|：10 网 8/10 更准或同量级，
      唯一稍差的 Fossolo 是 1.19e-12 vs 5.68e-13（绝对量级无意义）；
   ④ solve_polished 抛光之后两条通路收敛到同一点（max|ΔH| ≤ 1.137e-13 ft）。
  ⇒ 记账口径：验收 1 **是"改判据后通过"，不是"按原门槛通过"**。引用时必须
    连 a/b/c 三条理由一起写，不许只写"通过"。

  City_D    0.07205   0.12176   0.17207 |   0.46003  |  6.38x

  本轮**保留 refine=2 不动**（与稠密通路同等待遇，§2 的归因论证才成立）。

 3.1 【F5】稠密基线自己有 6% 的自缚，必须点名（不然读者会把它算进倍数）
  稠密通路的精化残差写的是 (A*Hj^T).sum(-1) 而不是 torch.bmm - 是为了
  **批不变性**（逐元素乘再 sum 的归约次序与 B 无关；bmm 走 cuBLAS 的分块归约，
  同一场景在不同 B 下结果可能变），这是当初的有意选择，不是疏忽。
  代价（对抗审计 §2，ky4 B=256，节点 <node-13>，ms/轮）：
    chol 53.37 / cholesky_solve 5.49 / 残差 elem 3.61 / 残差 bmm 1.18
    ⇒ 每轮 77.06（elem） vs 72.22（bmm），**基线被自缚 6.3%**。
    换 bmm 后 ky4 B=256 dense 2.99958 → 2.79958 ms/场景，倍数 6.23x → 5.87x。
  ⇒ 所以：**倍数里有 6% 不是 cuDSS 的功劳，是稠密基线为批不变性付的钱。**
    区间下沿按 bmm 口径应记 5.87x（同节点），上沿同理约 8.4x。
    要不要给稠密通路也加一个 bmm 开关是 P4 的事，本轮不动（动了会改数值）。

  plan 成本（每(拓扑,批量)一次，不进迭代循环）：
    Modena  B=1/64/256 →  7.20 /  41.72 / 143.65 ms
    City_D  B=1/64/256 →  7.76 /  62.88 / 257.45 ms
    ky4     B=1/64/256 →  9.62 / 146.82 / 663.79 ms
  即 ~0.65~0.72 ms/矩阵、线性于 B，与 P0 的 ~0.98 ms/矩阵同量级。
