1.2 ★ 新发现（上一轮没查）：**NW_Model 上 A 不是逐位对称**
    仓库把"A 逐位精确对称"当**断言**（regression ⑨ check_symmetry.py：
    `max|A−A^T| == 0.0`，非容差），`_CudssSolveFn` 的伴随复用前向分解也正是
    靠这条（其 docstring 写"非对角两处取自同一段 -Pm[:, lk_both]、同序散射
    ⇒ 数值上逐位对称"）。实测：
      net        Nj    逐 Newton 轮 max|A-A^T|                  >=3 条链路的节点对
      NW_Model  8566   4.44e-16 8.88e-16 7.11e-15 7.11e-15 2.84e-14   **40 对**
      NW_Model1 8566   （末轮 2.84e-14，16 个不对称槽）              40 对
      KL         935   0 0 0 0 0 0                                    0 对
      ky4        959   0 ×9                                           0 对
      ky8/ky2/ky13     0（同上）                                      0 对
    机理钉死了，并做了**最小复现**（a7_sym_minimal.py，两个 junction 的 4 行网）：
      case                        Nj  L   max|A-A^T|    逐位对称?
      2 条并联（同向）             2   3   0.0000e+00    是
      **3 条（2 正 1 反）**        2   4   **1.7764e-15  否**
      3 条（全同向）               2   4   0.0000e+00    是
      **4 条（2 正 2 反）**        2   5   **7.1054e-15  否**
    ⇒ 触发条件是 **同一对节点 >=3 条链路且方向不全相同**。装配把 (i,j) 与 (j,i)
      两块用**同一段** vals 散射，反向那条在两个槽里的**出现次序相反**；
      2 个加数的浮点和天然可交换（a+b == b+a 逐位），>=3 个才会差位。
    ★ 而 check_symmetry.py 自带的合成拷问网，注释里明写的是
      "parallel pipes (**two** links on the same node pair)" - **恰好 2 条**，
      所以这条守卫**结构上就测不到**这个情形。NW_Model 有 40 对这样的节点对
      （最多 4 条），是第一个把它照出来的网。
    量级：绝对 2.84e-14，元素量级 ~1e1~1e2 ⇒ **1 ULP**，数值上无害；
    但它意味着：
      (a) 把 NW_Model 加进 check_symmetry.py 的网表，regression ⑨ **会变红**；
      (b) _CudssSolveFn 那句"逐位对称"在主线网上要改成"对称到 1 ULP"。
    ⇒ 这不是"算错了"，是**主线网会把仓库自己的不变量证伪**。要么在装配里
      对反向并联链路定序（让两块同序），要么把断言改成 1-ULP 容差并改文案。

§2 审阅项 2：OOM 边界是真的吗
================================================================================
脚本 scripts/p5_bignet/audit/{a2_chol_thresh.py（本机）, aud_gpu_a2.py,
     aud_gpu_a4.py（集群）}。每个候选**全新子进程** + CUDA_LAUNCH_BLOCKING=1，
并逐条打印 **/proc/self/status VmHWM**（主机侧峰值）与子进程 returncode，
用来分开"torch 报 OOM"/"AcceleratorError"/"被信号杀（换页/OOM-killer）"。

2.0 先说结论：**门槛数值全部复现，但它的"身份"被认错了。**

2.1 复现（给上一轮记功）
    a) 逐点扫（**不二分**，因为二分预设单调）在 RTX 5090（<node-15>）上：
       B=1  : Nj=4096…8566 **全 OK**
       B=2/3/4/8 : Nj<=6016 OK，**Nj>=6017 起全部 AcceleratorError
                   (CUDA error: invalid argument)**，一路到 8566
       ⇒ 门槛 = **Nj 6016/6017，与 B 无关**，与上一轮二分结论**逐位一致**，
         而且我确认了它**确实单调**（二分没被非单调坑到）。
    b) 失败性质：**全程没有一次"被信号杀"**（rc 从来不是负数），主机 VmHWM
       稳定在 0.79~1.42 GB - **不存在换页/OOM-killer**。撞的确实是
       device 侧：要么 torch.OutOfMemoryError，要么 AcceleratorError。
       上一轮"这不是显存不够"的判断成立（B=2 只要 1120 MiB，卡上空闲 31603 MiB）。
    c) 理论算术核对（Nj=8566, nnz=27760）：
       B=256 稠密 A = 150,274,777,088 B = **139.9543 GiB**（工单说的 140 GB，对）
       B=256 CSR 值 =      56,852,480 B = **54.2188 MiB**
       比值恒为 Nj²/nnz = **2643.2x**
       （上一轮报 139.90 GiB / 54.25 MiB，与精确值差 0.04%/0.06%，不影响结论。）
       另记：BWSN_2（Nj=12523）B=256 的稠密 A 要 **299.12 GiB**。

2.2 ★ 订正一：**那不是"稠密的墙"，是 torch.cholesky_solve 一个 API 的墙。**
    同一个 (Nj,B) 上把算子换掉，5090 / 4090 上都一样（aud2_1460594/1460596）：
      Nj=8566 B=2/4/8  torch.linalg.cholesky            **OK**
                       torch.cholesky_solve             **FAIL invalid argument**
                       solve_triangular ×2（等价回代）   **OK**
                       torch.linalg.solve（LU）          **OK**
      Nj=8192 同样；Nj=6016 全部 OK。
    也就是说：**两次 solve_triangular 就绕过去了，一行代码的事。**

2.3 ★ 订正二：**换一版 torch，这堵墙根本不存在。**
    本机 RTX 5060 Laptop（Blackwell, 8 GiB）+ **torch 2.13.0+cu132 / CUDA 13.2**，
    同一段代码逐点扫 Nj=4096…8566 × B=1,2,4：**cholesky_solve 全部 OK，一次都没挂**。
    集群那两张卡（5090/4090）用的是**同一个** torch 2.11.0+cu128 构建 -
    所以上一轮"5090 与 4090 双卡复现"只证明了"与卡无关"，**没有**证明
    "与 torch 版本无关"。
    ⇒ **主线绝不能写"稠密通路在 Nj>6016 跑不了 B>=2"。** 那是
      torch 2.11.0+cu128 的一个缺陷，2.13.0+cu132 上已经没有。

2.4 ★ 拆掉这两处以后，稠密**真正**的天花板（aud4_1460605，5090 <node-06>）
    NW_Model（Nj=8566）纯前向，每个 B 全新进程：
      变体      最大可跑 B   首个失败 B   失败性质        该 B 的 ms/场景  peak_alloc
      ship 原样      1          2       CUDA invalid arg   700.70 ms      2246 MiB
      tri（换回代） **10**      12      **真-显存 OOM**    677.53 ms     22457 MiB
      tribmm（再换 bmm 残差）**10**  12  真-显存 OOM       669.76 ms     22457 MiB
      cudss 对照   >=1024（未触边界）                       0.5626 ms     4759 MiB
      cudss B=256                                            0.5092 ms     1209 MiB
    4090（24 GiB，aud4_1460606，<node-03>）同口径：
      ship 最大 B=1（B=2..12 invalid arg、B=14 cusolver INTERNAL_ERROR、B=16 真 OOM）
      tri / tribmm 最大 **B=8**（B=10 真-显存 OOM），956.30 / 943.52 ms/场景
      cudss 到 B=1024 OK（0.7122 ms/场景），B=256 最优 0.6320 ms/场景
    两节点的诚实倍数（各取各自最优批）：
      5090 <node-06>  稠密 669.76 ms/场景(B=10) vs cudss 0.5092(B=256) = **1315x**
      4090 <node-03>  稠密 943.52 ms/场景(B=8)  vs cudss 0.6320(B=256) = **1493x**
      同批 B=8：5090 681.77 vs 1.8126 = 376x；4090 956.30 vs 3.0091 = 318x
      B=1：    5090 700.70 vs 12.73 = 55.0x；4090 1092.37 vs 20.99 = 52.0x
    ⇒ **主线那句话的诚实版本应该是：**
      "在 NW_Model（Nj=8566）上，稠密通路受显存限制最多做到 **B=10**（32 GiB 卡）
       / **B=8**（24 GiB 卡） - 每场景 0.68 s，而且**几乎不随 B 摊薄**
       （B=1 的 0.70 s → B=10 的 0.68 s，只省 3%）；cuDSS 到 B=1024 仍稳定，
       每场景 0.56 ms。批量能力差 **~100 倍**，单场景吞吐差 **~1200 倍**。"
 - 不是"稠密只能 B=1、差三个数量级"。B=1 那个数是被一个 torch bug 造出来的。
    附带反证一条（我自己的猜想被实测打脸，如实记）：我原以为仓库刻意避开 bmm 的
    残差写法会多占一整块 [B,Nj,Nj]、压低最大 B。**实测 tri 与 tribmm 的
    peak_alloc 逐字节相同**（2278/4521/9007/13488/17973/22457 MiB），最大 B 也
    同为 10，时间只差 1.1%。⇒ 这处**不是显存自缚**。

2.5 ky8 的显存墙：**上一轮的数字是对的**
    5090 上 ship 最大 B=**464**、B=480 真-显存 OOM（peak 25114 MiB） -
    与上一轮"464 可跑 / 465 起 OOM"一致。tri 变体同为 464 ⇒ Nj=1325 < 6016，
    没有 API 那道坎，撞的确实是显存。**两种墙必须分开写**这条结论成立。

6.0 先把"能不能用"这一条补上（上一轮 §4.5 留的口子）

    accuracy=1e-14/max_iter=30，损失 = 随机权 w·H_junction）：
      一次前向+反向 24.0 s，|g|_max=2.0967e+02，|g|_2=4.4556e+03，全有限
      伴随 vs 中心差分（4 个坐标：|g| 最大 2 个 + 需水最大 2 个）
        node 425   2.096730e+02 vs 2.096730e+02   rel 9.72e-09
        node 424   2.096681e+02 vs 2.096681e+02   rel 5.39e-10
        node 2035 -3.042810e+01 vs -3.042810e+01  rel 3.92e-09
        node 1510 -2.704116e-01 vs -2.704116e-01  rel 3.90e-08
      **最差相对误差 3.897e-08 ⇒ PASS（门槛 1e-6）**
    同时复核了上一轮自报的 unrolled 体检，结论一致：
      unrolled_grad_health(K=5) = {verdict:'不建议', rel_K:1.0000000001,
                                   gmax:2.435e+11, param:'demand'}
      （上一轮报 gmax=5.04e20，树不同、量级不同，但 verdict 与 rel_K=1.0 一致。）
    ⇒ **NW_Model 拿得到可用梯度，但只能走 ImplicitGGASolve。**
      这条不是"不能当主线"，是"正文写反向时必须点名走哪条路"。

6.1 判定：**够格，但只能当"规模轴"的主线，不能当"能力轴"的主线；
     而且交付前有三件事必须先做。**

  支持它的（都是实测）：
   · 它是整批 collection 里 **唯一一个 Nj>2500 且我们的 epanet 通路与官方 DLL
     逐位相同（0.0 ft）、迭代数也相同（5/5）的网**。对照组：
       BWSN_Network_2（Nj=12523）epanet vs DLL **max|ΔH| = 33.58 ft**，
                                  迭代数 7 vs 10 - 状态机分歧，现在对不上
       PacificCity  （Nj=8715） epanet vs DLL **max|ΔH| = 2.36e+07 ft** - 直接发散
     ⇒ 大网里**只有 NW_Model 的参考解现在立得住**。
   · κ(A)=7.26e10（去死支 1.79e10），**比现网表里的 KL 好一个量级、比 ky13
     好三个量级**（§1.4）。规模没有把条件数拖坏。
   · 物理残差（自己重算，不信 dgga）：K>=20 时开管能量残差 1e-8 ft、
     相对 3.3e-10；连续性 5.7e-07 cfs（§1.3）。
   · ImplicitGGASolve 的梯度与 FD 对到 3.9e-08（§6.0）。
   · 结构上"零水池、零阀门、3 泵"正是它能进 dense 的原因 - 单帧稳态很干净。

  反对它当"唯一主线"的（也都是实测）：
   · **许可最弱**：上游 OpenWaterAnalytics/epanet-example-networks **没有
     LICENSE 文件**（GitHub license=null）。而同尺寸的 PacificCity 是
     CC-BY-3.0、L-TOWN 是 CC-BY-4.0。重分发这份 .inp 没有明确授权（§5）。
   · **没有一次文献**：它是上游回归测试集里一个叫 "Northwest System" 的匿名
     模型，没有论文、没有城市。BWSN_2 至少挂着 BWSN 2008 竞赛。
   · **它一个难特性都不考**：零水池、零阀门（无 CV/PRV/PSV/FCV/TCV）。
     用它当主线，等于主线**完全绕开**并发那位正在补的整个特性门。
     论文若要说"能处理真实配水网"，只有一个"全是管+3 台泵"的大网撑着，
     是审稿人一定会戳的地方。
   · 它会把仓库自己的**逐位对称不变量**证伪（§1.2，40 对 >=3 链路的节点对）。

   (b) 参考解不要用 INP 自带的 ACCURACY=0.01（5 步） - 那一步的开管能量
       失衡是 3.3e-2 ft。收到 K>=20 / ACCURACY<=1e-6（§1.3）。
   (c) §2 那两句主线话要改写（见 §2.4）。

6.2 要不要等 BWSN_2（Nj=12523）
  · 好消息：CVPIPE 落地后，**BWSN_2 离 dense 只差 5 条链路**（PSV×1 + FCV×4，
    占 14831 条的 0.03%）。我实测确认了这个门是 {PSV, FCV}，别的都过。
  · 坏消息（上一轮没测、我测了）：**光开门不够。** 现在 BWSN_2 的
    `mode="epanet"` 与 DLL 差 **33.58 ft**、迭代数 7 vs 10 - 与 ky2/ky8/ky13
    同病（状态机分歧）。也就是说 PSV/FCV 支持做完之后，还得先把这个网的
    参考解对齐到 DLL，**才谈得上拿它当主线**。这不是"再等一个特性"，
    是"再等一个特性 + 一轮状态机对齐"。
  · 所以：**不要等。** 现在就用 NW_Model 撑规模轴（8566，比 ky4 的 959 大 8.9 倍），
    同时把 BWSN_2 列为下一目标；等 PSV/FCV + 状态机对齐都过了，再把主线
    换成 BWSN_2（Nj=12523，且有可引用的一次来源）。
  · PacificCity（8715、CC-BY-3.0、有一次文献）短期没戏：25 条 PRV 之外，
    epanet 通路本身就发散（2.36e7 ft），要修的不止一道门。

6.3 一句话交付
    **NW_Model 够格，但要带三条括号交付**：
    (1) 它是"最大且参考解立得住"的网，不是"最难"的网 - 零水池零阀门；
    (2) 它的批量优势必须按 §2.4 的诚实口径写（稠密 B<=10 受显存限制，
        不是"B=1 撞 torch 的墙"）；
    (3) 它的许可与可引用性最弱，正文只能给 URL+commit+sha256，不能随文分发。
    **BWSN_2 不值得等**（差 5 条链路 + 一轮状态机对齐），但值得写进 roadmap。
