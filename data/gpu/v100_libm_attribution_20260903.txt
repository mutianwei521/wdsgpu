Iteration counts and link statuses agree in every one of them; only the values
drift at the 1e-7 .. 1e-5 ft level.

Why: dgga/solver.py deliberately calls msvcrt.dll pow/log through ctypes
(module-level _pow_crt/_log_crt) so that r_hw, the emitter coefficients and the
per-iteration head-loss powers are rounded exactly like the Windows EPANET DLL.
On Linux the except-branch falls back to math.pow/math.log (glibc).

1. pow/log probe (scratch pow_probe.py, 25000 bases in [1e-8, 1e4], exponents as
   used by the solver), Windows msvcrt vs Linux glibc, same inputs:
     pow_1.852000     mismatched     56/25000  max_ulp=1
     pow_0.852000     mismatched     46/25000  max_ulp=1
     pow_4.871000     mismatched     54/25000  max_ulp=1
     pow_-1.333000    mismatched     60/25000  max_ulp=1
     pow_0.900000     mismatched     51/25000  max_ulp=1
     pow_0.148000     mismatched     63/25000  max_ulp=1
     pow_0.539957     mismatched     39/25000  max_ulp=1
     log              mismatched      7/25000  max_ulp=1
   i.e. 0.03-0.25 % of the calls differ by exactly one ULP.

2. EPANET itself is not bit-portable either. Rebuilding two references with the
   Linux libepanet22.so shipped in the same wntr 1.5.0 (scratch libm_attrib.py):
     city_d      Windows-DLL vs Linux-DLL: 25 frames,   max|dH|=8.410e-06 ft, bit-equal heads 0.18 %, iterations equal
     pub_l_town  Windows-DLL vs Linux-DLL: 2031 frames, max|dH|=7.142e-06 ft, bit-equal heads 0.52 %, iterations equal

3. dgga on Linux against the Linux-DLL references:
     city_d      align.py (25 frames): max|dH|=2.109e-05 ft, max|dQ|=2.667e-06 cfs (FAIL at the 1e-6 gate)
     pub_l_town  frame 0 with status machine: max|dH|=7.926e-07 ft, max|dQ|=2.020e-07 cfs, iters 17/17, status equal (PASS)
   So the Linux .so does not match glibc-pow dgga any better than the Windows
   DLL does; the two EPANET builds themselves differ at the same magnitude.

Conclusion: the 1e-6 ft / 1e-6 cfs gates of regression_all encode a
same-CRT (msvcrt) comparison and are below the cross-platform scatter of
EPANET itself. On Linux the bit-level regression is not reproducible and the
Windows workstation stays the authority for regression_all; the Linux drift is
<= 2.1e-5 ft in head with identical Newton trajectories (iterations, statuses,
event sequence apart from the ky5 threshold crossings), which is irrelevant for
the GPU experiments (placement, calibration, leak inversion) that this server
is used for. The cuDSS path is validated on this server independently
(data/gpu/v100_regression_gpu_20260903.out, 54/54).
