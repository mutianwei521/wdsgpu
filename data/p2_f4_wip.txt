§0 结论先写
  1) 新接口：`s.cudss_free(empty_cache=False)`（返回释放份数）、
     `with s.cudss_session(): ...`（退出必放，含异常路径）、
     `s.cudss_cache_info()`（每份的 B/dtype/device/matrix_type/plan_ms/建立期 MiB）。
  2) 缺省行为：`s.cudss_cache_max = 8` 的 **LRU 有界缓存**（None = 不限 = 修复前）。
     8 这个数是**测出来定价**的，不是拍的，见 §3。
  3) 缺省 dense/dense 通路一行没碰；regression_all 前台 **50/50 PASS**（§6）。
  4) **一条必须写清楚的限制**：`DirectSolver.free()` 并不把字节还给驱动，
     只还给一个**可复用池**（§2）。所以"调用后设备内存真的回落"这句话要按
     **常驻水位**理解，不是"归零"。而常驻水位正是 OOM 的决定量，且它确实被
     逐出策略钉死了（§4）。

§1 改了什么（dgga/solver.py）
  · self._cudss_cache: dict → collections.OrderedDict；命中时 move_to_end。
  · _cudss_release(st)：**先** solver.free() **再**丢 torch 侧 vals/rhs/a/b/vviews。
    顺序不能反 - a_list 里 sparse_csr_tensor 的 values 是 vals 的行视图，
    cuDSS plan 时记的就是这些指针；先放缓冲再 free() 等于让库在已归还的显存上收尾。
    （free() 自己会先 wait 上一次计算事件，direct_solver.py:1859 起，无需额外 sync。）
  · _cudss_evict()：把缓存压回 cudss_cache_max 份（LRU 从最久未用端逐出）；
    cudss_cache_max<1 → ValueError，=None → 不逐出（即修复前行为）。
  · cudss_free() / cudss_session() / cudss_cache_info()：见 §0。
  · _cudss_state() 顺手记下该份 state 建立期的设备内存增量 dev_mib（给 cap 定价用）。
  · cudss_plan() 的 docstring 补一句：预热同样受 cap 约束，想一次热 k 个批量
    先把 cap 调到 >=k。

§2 free() 到底还了什么：**进池，不进驱动**（1459303 §A + 1459312 pool）
  ky4，单位 MiB，"非torch" = mem_get_info 的已用 − torch.cuda.memory_reserved()
  （cuDSS 那块就落在这一列）。

  B     阶段                        设备已用   torch保留   非torch
  256   建 state 前                    610.2      22.0     588.2
  256   plan() 后                      836.2      22.0     814.2   (plan 1613.5 ms)
  256   首解后（含数值分解）             980.2     164.0     816.2   (iters 9)
  256   丢输入 + empty_cache()          838.2      22.0     816.2   ← empty_cache 无效
  256   cudss_free()                   804.2      22.0     782.2   (释放 1 份)
  256   再 empty_cache()               784.2       2.0     782.2
  1024  plan() 后                     1396.2      68.0    1328.2   (plan 4474.7 ms)
  1024  首解后                        2010.2     682.0    1328.2
  1024  丢输入 + empty_cache()        1376.2      48.0    1328.2
  1024  cudss_free()                 1342.2      48.0    1294.2
  ⇒ 一份 state 的非torch 占用：B=256 **228.0 MiB**、B=1024 **546.0 MiB**
    （首份含 cuDSS 一次性初始化；边际份见 §4 的 97.6 MiB@B≈216）。
  ⇒ `torch.cuda.empty_cache()` 对这一列**一个字节都收不回**（816.2 → 816.2），
    审计 F4 的这句判断完全成立。
  ⇒ **但 cudss_free() 也只让设备已用掉了 34.0 MiB**（816.2 → 782.2）。
    剩下的去哪了？进了一个可复用池。三条证据（1459312 pool，全新进程）：
      a) 同一 B=256 释放-重建 **20 轮**：建后恒 816.2 / 释放后恒 782.2，
         **完全不单调**，没有任何泄漏；
      b) 跨 B 复用：建 B=256(816.2) → free(782.2) → 建 B=1024 得 1328.2，
         与"全新进程直接建 B=1024"的 1328.2 **一模一样** - B=256 的那块被
         B=1024 整块吃掉了，不叠加；
      c) cudss_cache_info() 报的 B=1024 建立期增量 512.0 MiB 与上面一致。
  ⇒ 所以正确的说法是：**cudss_free() 把"常驻"降下来了，把"进程占的水位"留在
    高点**。对 OOM 而言起决定作用的是常驻（新分配能不能从池里拿到），§4 直证。
    这条限制**必须写进文档**，不能用"调完就回落"一句话糊过去。

§3 缺省 cudss_cache_max=8 的定价（1459312，每策略一个全新进程）
 3.1 形态一：B∈{1,8,64,256} 轮转，6 轮（ky4）
  策略        中位轮耗时     plan 总数   free 总数   末轮非torch
  cap=None      232.4 ms          4          0       944.2 MiB   ← 修复前
  cap=1        1465.7 ms         24         23       848.2 MiB
  cap=2        1467.4 ms         24         22       880.2 MiB
  cap=4         232.0 ms          4          0       944.2 MiB
  cap=8         229.3 ms          4          0       944.2 MiB
  **上限 < 轮转周期 ⇒ LRU 次次 miss**：cap=1/2 每轮从 232 ms 涨到 1466 ms
  （**6.3x**），换来的只有 96 / 64 MiB。这是典型的 LRU 周期性抖动，任何
  计数式策略都躲不掉，只能靠"上限 ≥ 周期"。

 3.2 形态二：每 epoch = 4×B=256 + 1×尾批 B=37，4 个 epoch（最常见的变批量）
  策略        4 epoch 总耗时   plan   free   末非torch
  cap=None       3250.8 ms       2      0    848.2 MiB   ← 修复前
  cap=1          6644.4 ms       8      7    848.2 MiB   ← **2.04x，且一分钱不省**
  cap=2          3239.2 ms       2      0    848.2 MiB
  cap=8          3258.0 ms       2      0    848.2 MiB
  ⇒ 上限 1 直接砸掉一半吞吐，省下的显存是 0（末态一样）。**缺省不能取 1。**

 3.3 逐出后重进的单价（1459303 §E，ky4，节点 <node-20>）
  B=64 : 命中 51.4 ms  / 未命中 264.0 ms  ⇒ 重建 212.7 ms = 3.32 ms/矩阵
  B=256: 命中 124.0 ms / 未命中 1102.1 ms ⇒ 重建 978.0 ms = 3.82 ms/矩阵
  对照常驻代价：B=256 一份 228 MiB。**拿 228 MiB 换 0.98 s** - 上一步刚把
  ky4 B=256 的整解峰值从 7302 MiB 砍到 135 MiB（P2 §5/审计 §4），
  现在回吐 0.2 GiB 去省一秒，是明显划算的一笔。

 3.4 为什么是 8 而不是 4 或 16
  · ≥4 就够覆盖 §3.1/§3.2 两种形态（cap=4 已与不限逐项同表现）；取 8 留一档
    余量：分桶式 DataLoader 常见 4~8 个桶，课程式变批量也在这个量级。
  · 上限本身是**硬界**：最坏占用 = 8 × 单份。单份可由 cudss_cache_info() 读到
    （ky4 B=256 → 228 MiB，B≈216 的边际份 → 97.6 MiB），所以 8 份在 ky4 上
    最坏 ~1.8 GiB，对 32 GiB 卡是可接受的常驻。要更省就自己调小。
  · 不做"按显存预算逐出"：单份占用只能透过全局 mem_get_info 观察，而那个数
    会被同卡上任何别的分配污染（§2 的池复用还会让它偏小甚至为 0），
    做成缺省会不可复现。计数式上限是确定的、可复算的。
  · 轮转周期 k>8 的 ragged 场景：调大 cap 或在数据侧分桶/补齐。
    **cuDSS 的 plan 按 (拓扑, B) 定死**（nvmath 1.0.0 只有显式批量，P0 已查），
    批量数就是 plan 的份数，这一点靠缓存策略换不掉。

 4.3 一句话总结这两张表
  逐出策略把「常驻 ∝ 见过的不同批量数」变成「常驻 ≤ 上限 × 单份」，
  而在 ragged/大批量这两种真会出事的形态里**一分钟都没多花**（75.4 vs 74.9 s、
  250.8 vs 250.0 s） - 因为那些形态本来每个批量就要重 plan，逐出并不额外增加
  plan 次数。真正要小心的是 §3.1 那种**周期性轮转**：上限必须 ≥ 轮转周期。
