## 3. 哪些逻辑天然串行 / 哪些可向量化
天然串行（依赖上一次迭代的标量判断或全局顺序）
 S1 linsolve 零主元 → _badvalve → continue 重试同一迭代（:1262-1271）。
    批量致命点：torch.linalg.cholesky 对批内任一样本非正定就整批抛异常，
    没有"只重试第 b 个样本"的语义。要么 per-sample 掩码 + torch.linalg.cholesky_ex
    的 info 分支，要么把 CBIG 罚函数换成不产生零主元的写法。
 S2 dqsum/qsum 的左折叠求和（:1284-1285，`sum(np.abs(dq).tolist())`） -
    纯为位级复刻 C 的舍入次序，可微路径不需要，torch.sum 即可。
 S3 _pswitch（:1115-1150）：同一链路被多条控制命中时后者覆盖前者，
    是"最后写入者胜"的顺序语义。控制数很少，可用 segment-last scatter 化解。
可向量化（其实与串行无关，只是写成了 python 循环）
 V1 _cvstatus/_pumpstatus/_fcvstatus/_prvstatus/_psvstatus 全部是
    (当前状态, dh, q, h1, h2, hset) 的纯逐元素分段函数 → 嵌套 torch.where 直译，
    天然支持 [B,L] 且允许同一阀在不同场景取不同状态。
 V2 _linkstatus 的 `for k in range(L)`（:1093）链路之间无依赖，可整体向量化。
 V3 _tankstatus 的 n1/n2 交换（:1064-1070）只依赖静态拓扑 is_fixed_node/is_tank_node，
    可预计算成静态 tank 端索引 + 符号；剩下全是 H 的比较。
 V4 _valvecoeffs 的"顺序依赖"只是装配两趟（先 link+node，后 valve），不是逐阀串行；
    ACTIVE 分支里的 `if Xf[a2]<0` 是逐元素数据相关分支 → torch.where。
 V5 _dw_PY_np（:635-682）逐管道 python 循环，公式纯逐元素 → 直接 torch 化。
 V6 _curvecoeff（:683-706）的 while 查段 → torch.searchsorted（批+泵两维）。
关键结论（批内状态不齐怎么办）
 EPANET 的状态只以两种方式进线性系统：
  (a) 改逐链路的 (P,Y) 标量对（关闭支 1/CBIG、开启支 valvecoeff、泵支 pumpcoeff）；
  (b) 改装配时往 Aii/F/Xflow 加的**值**（ACTIVE PRV/PSV 的 CBIG 罚函数、FCV 的 ±qs）。
 两者都不改变**索引结构** - A_idx/f_idx1/f_idx2 是静态的。所以批内状态不同
 只需把"按状态挑链路"改成"(B,L) 布尔掩码乘 0/1 后照常 scatter_add"，
 每迭代按最坏情况装配（ACTIVE/OPEN/CLOSED 三支全算再 where 选），
 代价是常数倍算力，不是结构性障碍。真正的结构性障碍只有 S1。

## 4. ImplicitGGASolve 的泵梯度到底支持到什么程度
签名 autodiff.py:565-567：(demand,res_head,ke,r_hw,solver,accuracy,max_iter,
polish_steps, speed, pump_h0, pump_r, status)
- forward :565-596 → solve_polished :491-547 → s.solve(...)（:518）。
  含泵网在 GGASolver 构造期就被 dense 拒（solver.py:104-110），所以只能传
  mode="epanet" 的 solver ⇒ **前向是逐场景 numpy 串行**，不是批量 torch。
  之后 _polish_np :425-444 对每个 b 用 scipy splu 做整装 Newton（solve_polished :530 `for b in range(B)`）。
- backward :599-670：`for b in range(B)` :616 + splu(J).solve(v, trans="T") :633，
  scipy 稀疏 LU，逐样本、CPU。泵 θ 的 ∂F/∂θ 在 :655-659，
  由 _pump_coeffs_np :74-171 给出 dw=∂φ/∂ω、dh0=∂φ/∂H0、drp=∂φ/∂R；
  钳位支/关闭支导数置 0（:103-107 等）。
- status 是**冻结**的 int8[L]（_resolve_pump_args :61-71），不是微分量：
  梯度是"给定状态下"的隐函数导数，状态切换本身对梯度无贡献。
- ACTIVE PRV/PSV 的能量行被换成水头约束行：_valve_act_masks :173-189、
  _residual_np :364-372、_build_J :383-419；被约束端为定水头则 raise（:185-189）。
- 验收脚本：scripts/audit_prv_dw_adversarial.py:101 建的是 mode="epanet" solver，
  :177 调 ImplicitGGASolve 传 (speed=K, status=S)；对拍中心差分。
  scripts/gradcheck_3way.py:81/188 用的是 mode="dense"（无泵网）。
⇒ 结论：泵/PRV/PSV/FCV 的梯度**已经有了**，但整条路都在串行 numpy/scipy 上；
  论文里"批量可微"的那条路（dense / solve_unrolled）并不含这些特性。

## 5. 附带发现：solve_unrolled 是被低估的半成品
autodiff.py:696-967，torch 批量展开（B 维在最外层，装配与 dense 同款 scatter）。
- 它只读 GGASolver 的**静态属性**（A_idx/f_idx1/lk_both/km_tcv/junc_nodes_t...），
  这些在 __init__ 里无条件构建（solver.py:178-205），所以它可以直接挂在
  mode="epanet" 的 solver 上跑 - 即"批量 torch + 有泵网"这条路已经通了一半。
- 已有的：泵三型 P/Y 的 torch 复刻 :817-895（CONST_HP/POWER/线性/CUSTOM/NOCURVE）、
  恒功率半步防穿零 :921-924、冻结 status 支 :730-735、ω=0 并入关闭支 :754。
- 缺的：
  · PRV/PSV/FCV 完全没有分支 - 非 TCV 阀会掉进 P_pipe（:800-813，:815 只对 is_tcv 换支），
    而阀的 r_hw=0 ⇒ hgrad=0<RQtol ⇒ 走 RQtol 钳位支，km 还取的是 km_pipe。
    **静默给出错误结果，没有任何守卫**（solve_unrolled 不检查 link_type）。
  · D-W 没有（只写了 H-W/C-M 的 hexp 幂律 :800）。
  · CUSTOM 泵选段是 python 双重循环 `for k in custom_links: for b in range(Bq)`
    （:853-866），每迭代都 .cpu().numpy() 一次 ⇒ O(K·B·泵) 的同步开销，
    是批量化的现成瓶颈（改 searchsorted 即可）。
  · 无状态机（status 冻结传入），无 tank 逻辑（tank 只作定水头节点消费）。
