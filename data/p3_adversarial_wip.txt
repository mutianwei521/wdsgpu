§1 梯度真的对吗（审计项 1） - 对
 1.0 先纠一个方法问题：**朴素 FD 量 ke 是没有意义的**（我第一轮踩到）
   `has_em = ke_j > 0`，对 ke=0 的节点做中心差分，+h 那步把发射器打开、−h 那步
   关着，前向在该点**本来就不连续**。实测 Hanoi B=1：解析 −1.028e+03，FD 给
   +1.208e+10（rel 1.000e+00） - **dense 解析给的是同一个 −1.028e+03**。
   ⇒ 这不是稀疏通路的问题，是 FD 越过了不可微点。上游 §1.1 用"|解析梯度| 过
   60 分位"的筛选恰好把这些坐标滤掉了，所以没暴露；但那条筛选也因此**无法证明
   小梯度坐标是对的**。我改成：方向只落在 ke>0 的节点上、且用**相对步长**
   （v_i ∝ base_i，永不穿零）。修正后 Hanoi B=1 ke：FD 收敛到 −3.052747e+03，
   rel 2.358e-07；穷举逐坐标（5/5 个活发射器）rel 3.655e-07。

   requires_grad 走 cudss → `NotImplementedError: ...导入失败：ModuleNotFoundError
   ("No module named 'nvmath')。请 pip install nvmath-python[cu12]，或显式改用
   linear_solver='dense' - 不做静默降级`。no_grad 前向同样 raise。**没有偷偷退回 dense。**
 7.3 不支持的参数/网型：PRV/PSV/FCV 网（BWSN_Network_2 / C-Town_BATADAL / D-Town）
   走 cudss 与走 dense **报同一个 NotImplementedError**，不做近似。
   （上游 §F 那行"NO RAISE"是探针选了 Net2 - Net2 只有 40 根 PIPE，本来就该放行。）
 7.4 一条**真实的不可微点**（两条通路共有，非 P3 引入）：ke=0 的节点上解析梯度是 0，
   而右侧导数是 ~1e10（发射器被打开）。见 §1.0。文档里没提。

 D1【文档/口径】§4 显存表只报 torch 峰值，漏 cuDSS 自己的 68~740 MiB。
    建议：表里加一列"cuDSS 非 torch 常驻"，倍数按合计重算（§4.1 已给全表）。
 D2【计数器诚实性 + 性能悬崖】槽被 LRU 逐出后，`_cudss_adjoint` 走
    `_cudss_state(...)` 会**重建 DirectSolver 并重做 plan()**，而计数器只记
    `bwd_refactorize`。实测（aud6，节点 <node-21>，K=8 slots=8）：
      Modena B=128：干净 fwd+bwd 127.0 ms → 逐出后**光反向 930.9 ms**（7.3x），
                    lib 报 bwd_refactorize=8，实际 plan()=8
      ky4    B=128：干净 fwd+bwd 138.8 ms → 逐出后**光反向 3702.2 ms（26.7x）**，
                    同样 8 次 plan() 被记成 8 次 "refactorize"
    梯度仍是对的（3.799e-08 / 8.705e-05，落在抖动里），所以这是**性能问题不是
    正确性问题** - 但它在计数器里完全隐形。
    建议：加 `bwd_replan` 计数（或在 `_cudss_state` 里对"可微图存活期间的 miss"
    单独计数），并在 `cudss_grad_slots` 的注释里写明"逐出的代价是 plan 不是 factorize"。
 D3【预热接口】`cudss_plan(B)` 只建 slot 0。实测 slots=6 时，`cudss_plan(128)`
    之后第一次可微 fwd+bwd 仍要现做 **5 次 plan、733.2 ms**，第二次 94.6 ms
    ⇒ 首步多付 **638.7 ms**。建议 `cudss_plan(B, slots=None)` 一次热到 slots 份，
    或在 docstring 里点名。
 D4【表述】§6.1 的 5.4x~5.8x 与 12~17.5x 只在 <node-01> 上量过（cuDSS 最快的一台）。
    跨节点实测：真实线代倍数 **3.8x~5.8x**、手写伴随对通用 autograd **6.3x~15.4x**。
 D5【表述】F4 的"耗时相同"是纯前向口径；带反向的 ragged 循环里缺省 cap=8 多付 **10.4%**。

§9 对 P4（回归 + 全面重测 + 文档）该测什么的独立建议
 R1 把 §1.4 的 **A 对称性断言写进 regression_all**（每网每轮 max|A−A^T|==0）。
    整条伴随的合法性挂在它上面，而它现在没有任何自动化保护 - 将来谁在装配里
    加一项只落单侧（比如 PRV 的罚函数行、或非对称的阀模型），前向照样收敛、
    梯度会静静地错。这是**最高优先级**。
 R2 回归里加"**复用即核对**"的断言：跑一次 slots≥K 的可微解，断言
    `bwd_refactorize==0` 且每次 reuse 时 `st["vals"]` 与 saved data 逐位相等。
    CPU 上没有 cuDSS，所以这条只能在 GPU 作业里做 - 建议做成独立的
    `regression_gpu.py`，与 regression_all 分开，缺 nvmath 时 SKIP 而不是 FAIL。
 R3 **抖动基线要先建，再定判据**。P2/P3 反复用"落在抖动底里"做结论，但抖动底
    本身没有被制成表。建议 P4 先出一张 `self-rerun jitter` 表
    （网 × B × 参数 × 通路，各重跑 5 次取 max），以后所有"vs dense"的判据都写成
    "≤ 该格抖动底 ×3"，而不是固定的 1e-8。§1.5 的做法可直接复用。
 R4 **给 City_D / ky4 的 grad d 一个明确的"不支持"结论**，别再只归因。
    实测在 κ≥7e8 的网上 unrolled 的 demand 梯度重跑自己都差 1e-3~1e-2、
    未收敛 K 下两条通路范数差 16 倍。建议：要么在 solve_unrolled 里对
    `max|g|` 超阈值时发 warning，要么在文档里写死"这类网用 ImplicitGGASolve"。
 R5 显存重测**统一口径**：torch 峰值 + 非 torch 常驻 + 扣掉 CUDA 上下文，
    每配置全新进程（scripts/p3_adversarial/aud4_gpu.py 可直接用）。
    顺带把 dense 那侧 230 MiB 的常数工作区也报出来，否则小网的倍数会虚高一倍。
 R6 **跨节点必须成对**：凡引用倍数，至少两台节点、且 cudss 侧与 dense 侧分别报。
    已知 cuDSS solve 地板跨节点 2.5~3.9 ms（1.56x），dense 侧 <1%。
    §6.1 那种"公平口径"表尤其要补第二台，否则倍数会被节点挑选左右。
 R7 训练回路里的**逐出压力测试**：真实训练有分桶 loader + 优化器状态，
    D2 那个 26.7x 的反向悬崖是会被触发的。建议 P4 加一个
    "ragged B + slots>1 + cache_max 刚好不够"的场景，量出端到端 step 时间的分布，
    并据此决定要不要把 `cudss_grad_slots>1` 时自动把 cache_max 抬到 slots+k。
 R8 文档：把 §7.4 的"ke=0 不可微"、D2 的"逐出=replan"、D3 的"预热只热 slot 0"
    三条写进 CONTRACT.md 或 solver.py 的模块级 docstring；这三条都是调用方
    踩得到、但看代码看不出来的。
 R9 **不要**在 P4 里顺手给稠密通路也写伴随（§6 说的那笔欠账）：它会改梯度数值，
    撞铁律三。要做就单开一个 `linear_solver='dense_adjoint'` 新开关，
    缺省不变，并用 §6.1/§3.2 这张表做验收。
