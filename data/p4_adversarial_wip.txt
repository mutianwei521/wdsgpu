§2 R1 的真缺口 - cuDSS 专属那段装配没有任何守卫（新发现）
--------------------------------------------------------------------------------
 2.1 结构：solver.py 里 `linear_solver == "cudss"` 分支有一段 CPU 上**不可达**的
   代码（emitter 对角 `csr_data.index_add(1, A_csr_diag, em/hgrad_e)` 那几行）。
   check_symmetry.py 是 CPU-only（不需要 CUDA/nvmath），所以这条分支它永远走不到。
   本机实测：往这里注入单侧写（X11），**72/72 全绿放行**。

 2.2 集群坐实（作业 1459838，节点 <node-13>，注入相对量 1e-9）
   P1 正品：cuDSS 真正拿到的 csr_data **逐位对称**
     Hanoi 8 轮 / Net3 10 轮 / Modena 14 轮 / ky4 7 轮，
     max|data−data^T| 全部 **0.000e+00**（好消息：现状是对的）。
   P2 注入后：
     net     max|data−data^T|  迭代数相等  max|dH|      regression_gpu.py
     Hanoi   1.180e-08         是          1.227e-08 ft  **PASS 40/40**
     Net3    3.647e-05         是          2.075e-06 ft  **PASS 40/40**
     Modena  4.463e-10         是          3.441e-08 ft  **PASS 40/40**
     ky4     1.633e-10         是          3.080e-07 ft  **PASS 40/40**
   ⇒ A 已经不对称到 3.6e-05，**全套 40 条断言一条都没红**。

 2.3 量级依赖（作业 1459848，节点 <node-02>，注入相对量 1e-2）
   同一注入放大到 1e-2 时才被间接抓到：ky4 迭代数从 7 跳到 100（不收敛）
   ⇒ T1 变红，regression_gpu **FAIL 38/40**；max|dH| 到 2.103e+00 ft。
   ⇒ 结论要写准：**cuDSS 分支的单侧装配只在"大到改变牛顿轨迹"时才被 T1
     间接看见；小扰动（正是最危险的那类，因为前向看不出来）完全没人查。**

 2.4 修法（一行量级，我没动代码）：把 §2.2 里 P1 那段探针搬进
   regression_gpu.py 做第四条 T4 - 拦 `_cudss_forward`，按转置槽逐位比
   `data`，判据 ==0.0。我的探针在正品上 4 网 39 轮全 0，成本可忽略。
   （或者给 check_symmetry.py 加一个"有 CUDA+nvmath 才跑"的 cudss 分支，
     但那会让它不再是 CPU-only，不如放 regression_gpu。）

§3 R2 - SKIP 是不是伪装的 PASS？三条断言真的在执行吗？
--------------------------------------------------------------------------------
 3.1 无 nvmath 环境（本机 RTX 5060 Laptop，有 CUDA 无 nvmath），前台实跑：
   打印"总判定: SKIP（退出码 2）"+ 缺什么 + "**本项 SKIP，不是 PASS**"，
   **实测退出码 = 2**。regression_all.py 不调用它（grep 无引用）⇒ 不会混进 51/51。
   ⇒ Python 脚本这一层：**合格**。

 3.2 **但 sbatch 包装把退出码吞了（真问题）**
   scripts/regression_gpu.sh 末两行是
       python3 -X utf8 regression_gpu.py
       echo "REGRESSION_GPU JOB DONE rc=$?"
   最后一条命令是 echo ⇒ **脚本本身恒退出 0**，作业状态永远 COMPLETED，
   无论 PASS / FAIL / SKIP。本地复现：`bash -c 'false; echo rc=$?'` 打印 rc=1、
   脚本退出 0。而模块 docstring 写的推荐用法就是 `sbatch regression_gpu.sh`。
   ⇒ 谁按作业状态接 CI，FAIL 与 SKIP 都会被当成通过。
   修法一行：`python3 ...; rc=$?; echo "... rc=$rc"; exit $rc`。
   （p4_remeasure/*.sh、p4_corrections/*.sh 同样，但那些是测量脚本不是判据脚本，
     严重性低。）

 3.3 集群哨兵证伪（作业 1459819，节点 **<node-13>** - 上游没用过的第三台）
   基线：原封不动全量跑，**rc=0，总判定 PASS 40/40**，
   且 T1/T2/T3 的**配置打印行数 = 10/10/20**（三条断言的循环体确实各自执行了，
   不是某条空转）。空哨兵（子集、零改动）rc=0 ⇒ 我不是把什么都弄红。
   6 个哨兵全部变红：
     哨兵                        期望  实得  红在   备注
     S1a cuDSS 精化 2→0          T1    RED   T2     **T1 没抓到**：迭代数没变
     S1b cuDSS 解 ×(1+1e-9)      T1    RED   T1     恰好只红 T1
     S2a bwd_refactorize 不自增  T2    RED   T2     正是"不数的计数器"，被反面断言抓到
     S2b 复用判据丢掉 gen 检查   T2    RED   T2     **T3 没抓到**，见 3.4
     S3a 前向返回前改 cuDSS 缓冲 T3    RED   T3     前向逐位不变，只有反向会错
     S3b "优化"掉重复的值搬运    T3    RED   T1,T3
   ⇒ 三条断言都有牙，**且 T2 的反面断言（slots=1 必须恰为 K−1）确实是必需的**：
     S2a 把计数器静音后，只查"slots 够时 refac==0"的话会全绿。

 3.4 两条要写进文档的边界（不是 bug，是断言的分辨率）
   (a) **T1 对"精化步数被改小"不敏感**：S1a 把 cudss_refine 2→0，
       10 个配置的迭代数一个没变，T1 全绿；是 T2 里那条
       `solve == K*(1+cudss_refine)` 的附带检查把它抓住的。
       所以"迭代数逐项相等"这条**不能单独**当线性解精度的守卫。
   (b) **T3 的探针是"重实现判据"而不是"观察代码"**：探针里那句 reuse 谓词
       是从 solver._cudss_adjoint 抄的。S2b 把 solver 侧的谓词放宽（丢掉 gen），
       探针仍按严格谓词判断 ⇒ 那些**真正被错误复用**的事件根本没进 T3 的比对，
       T3 全绿。整套仍然抓住了（T2 红），但 T3 单独不成立。
       修法：让探针读 solver 侧的判断结果（或把谓词抽成一个函数两边共用）。

§10 "这套东西现在能不能给外人用" - 我的独立判断
--------------------------------------------------------------------------------
 能，**但要带上三句话**：
 1. **缺省是安全的**：影子包 270 项逐字节、45 个梯度张量逐字节、regression_all
    51/51 - 打开 cuDSS 这条路不会动到任何人现有的数。这条我查得最死，站得住。
 2. **cuDSS 这条路本身"能用"但"守卫还差一块"**：R1/R2 的断言都真有牙（§1/§3），
    但 cuDSS 专属那段装配目前零守卫（§2），补上是一个函数的事。在补上之前，
    对外说法应该是"稀疏通路有 51+40 条自动断言，其中 A 对称这条只覆盖 CPU 可达
    的装配"。
 3. **性能宣传必须按他们自己写的两因子讲**：ky4 端到端 29x 里稀疏本身只有
    3.5~4.8x（等工作量口径 4.5~6.6x），Modena/City_D 上稀疏线代根本不赢。
    真正结构性的好处是显存（ky4 B=64 total 33.56x，我在第二节点逐位复现），
    以及由此打开的批量上限。README 已经这么写了，这点值得肯定。
 不建议对外的：`solve_unrolled` 的 demand 梯度在 City_D/ky4/Net3 上（§5.4 我
    独立看到 70% 的梯度差与跨节点漂移） - 他们自己已经判为"不建议"，
    但 README 的招牌速度表恰恰建在这三张网上，改文案前别拿这张表当卖点。
